# B135.83 — où les objets de dialogue disparaissent-ils ?

Sur la capture B135.82 du premier villageois, le décor et le cadre de
dialogue sont visibles, mais le walker a été appelé plus de 11 000 fois sans
jamais trouver d'objet C2. Une capture B135.81 plus tardive avait trouvé C2
non vide pendant 457 appels. Il faut donc mesurer **la création de la liste**
et sa destruction, sans supposer que le problème vient de `408BC`.

## Build

```sh
git fetch origin
git switch diag/b135.83-c2-creation
git pull --ff-only
cd 3ds
make clean
make profile -j4
```

Lancer `fm-new3ds-profile.3dsx`. Sur le premier villageois, prendre une photo
du cadre vide puis une autre après quelques pressions de B ou A. La bande
`B135.83 DIALOGUE CREATE DIAG` en haut de l'écran inférieur conserve les
compteurs depuis le lancement.

## Lignes nouvelles

- `create all/C2 gen` compte les entrées recompilées dans `800403D0`, dont
  celles avec `a1=1` qui devraient insérer l'objet en liste C2.
- `create C2 outer` voit les appels par le dispatcher principal. Les deux
  chemins sont nécessaires : un appel ARM imbriqué échappe au second.
- `idx`, `RA`, `head before` gardent les paramètres de la dernière création
  C2 pour retrouver son appelant dans Ghidra.
- `remove gen/outer` compte `80040530`, qui détache un objet ; `cat` est la
  dernière catégorie d'objet observée dans le chemin recompilé.
- `heads 0..6` montrent les sept listes à l'instant de la photo. Si d'autres
  listes sont non vides tandis que C2 reste à `-1`, la scène crée ses objets
  dans une autre catégorie ou n'initialise jamais la couche de dialogue.
- Les lignes B135.82 `live/ret`, `nodes/draw/bad`, `last GP0/422/424`
  continuent de retenir le dernier rendu avec C2 actif.

Ces sondes lisent seulement l'état guest. Elles n'écrivent ni dans la liste,
ni dans le GPU. Les compteurs d'entrée recompilée sont actifs en PROFILE.
